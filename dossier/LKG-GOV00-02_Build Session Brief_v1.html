Part 2

Scope and how it was run

Work started from screenshots of the live site on a phone showing square corners where the design called for rounded ones, a sticky "Book" button sitting on top of the page's own final "Book" button, and a price-estimate card whose figures visibly did not add up. From there the same standard was applied to the rest of the page: does every visible claim have something real behind it, and does every element render the way its own CSS says it should.

Verification standard used on every change

  • verify/preflight.py — the repository's own pre-publish script (script parses, no duplicate ids, exactly 34 page sections, no dangling getElementById targets, zero emoji, every called function defined, every var() token declared, AU compliance sentinels present) — run after every edit, must print RESULT: PASS
  • A real Chromium browser (Playwright, not a static read of the HTML) driven through every one of the 31 client-side routes, watching for uncaught JavaScript errors
  • Viewport checks at 360, 390, 400, 420, 430 and 1280px — the widths that matter for phones and desktop — checking for any element wider than the viewport
  • Screenshots taken and inspected at each fix, not assumed from reading the CSS

Everything reported as fixed in Part 3 passed all four checks before it was published. Nothing was shipped on the strength of "this should work now."

Part 3

Build log, v4.3 → v4.7

v4.3 — 19 Sep, 10:15 Done da7e53c

Square corners, site-wide. Ten CSS rules called var(--r-lg) — a token that was never declared anywhere in the file. A browser drops an undeclared custom property silently; no console error, nothing visibly broken in the source, the property just doesn't apply. Every one of those ten surfaces — the final call-to-action panel, the map card, the Kings Club card, segment cards, the marquee — rendered at radius zero instead of the intended 12–18px. Repointed each at the design system's declared scale.

Sticky "Book" button landing on the page's own "Book" button. The button used position:fixed, which normally pins an element to the browser viewport regardless of scroll. It had been placed inside a page section that runs a filled CSS animation on transform — and an element with an active transform becomes the containing block for anything fixed inside it, overriding the fix entirely. The button was scrolling with the page instead of floating over it, and came to rest on the final call-to-action panel. Moved outside that section; now genuinely fixed, and hidden specifically over the final CTA and the footer so it never again sits on top of another Book button.

Preflight gained a check for exactly this class of bug: every var() reference without a fallback must resolve to a declared property. Confirmed it fails against the pre-fix file with the same ten references, so this cannot ship unnoticed again.

Photo pipeline built (unrelated defect, same session) Done, later superseded bda125e, 8e3fc2d

Built tools/embed_photos.py to drop real photographs into the "how a collection actually goes" section, resizing to WebP and requiring alt text and a licence record before anything embeds. This tooling was built before the decision (v4.7, below) to remove the placeholder illustrations entirely. It was not wasted: the empty photo slot and the embed script are unchanged and ready the moment real photographs exist — see Part 5, decision 4's sibling note on photography in site/photos/README.md.

v4.4 — 19 Sep, 10:48 Done a5c8dc3

A CSS class meant two different things. One rule (.tab) styled the app's bottom navigation bar: flex-direction:column, centred content, and bottom padding sized to clear an iPhone's home-indicator safe area. A second, unrelated rule redefined the same class name purely to add tabular number spacing to price figures. Seven price spans on the home page and the Kings Club calculator carried this second, unintended meaning — so every number on those cards was laid out as if it were a navigation button, including roughly 34px of dead bottom padding per row on a real iPhone (that padding is 0 in a browser test harness with no safe-area inset, which is why this wasn't caught earlier). Renamed the number-spacing class to .tnum; the five real navigation buttons are untouched.

A background "glow" rendered as a flat coloured bar with a hard edge. The CSS used radial-gradient(circle, …) inside a box 60% as wide as the screen but 140% as tall — on a phone, roughly eight times taller than wide. A circle's falloff in that box is far wider than the box itself, so it painted as a solid rectangle rather than a soft glow. Changed to ellipse, which scales its falloff to both dimensions of the box it's in.

The total did not add up. The card showed $32 (one load) plus $13.50 (delivery), and a total of $73.50 — the $28 difference (the minimum-order top-up) was mentioned only in a footnote below the total, never in the sum itself. Added it as its own line item, shown only when it applies, computed from the same live pricing configuration as everything else on the card — no new figure was invented.

v4.5 — 19 Sep, 10:57 Done 8374e51

Removed the home-page coverage map outright. It rendered two hand-drawn shapes labelled "Brisbane" and "Logan" with 20 pins placed at hand-picked pixel coordinates that bore no relationship to real geography, under a heading reading "Live footprint across Brisbane & Logan" and body copy stating "Sixteen suburbs collecting today." Four of the twenty pins were marked in the code itself as // opening soon (mock, keeps the "growing" story alive). This was not adjustable to the Australia-wide instruction — it was deleted along with its supporting JavaScript and CSS. The coverage page (#/coverage) is unaffected and rebuilt properly in v4.6.

v4.6 — 19 Sep, 11:06 Done daaccbc

Every Brisbane / Logan / South East Queensland claim removed. 33 lines, roughly 104 occurrences, across the page <title>, meta description, Open Graph tags, the web app manifest, the top strip, the hero eyebrow and trust chip, the business and about and contact copy, the footer, every JavaScript-generated page title, and the schema.org structured data Google reads (areaServed was a list of 16 specific Queensland postal addresses; now {"@type":"Country","name":"Australia"}). Replaced throughout with "Australia's major cities and surrounds" — the principal's own wording. Assumption — no specific city or postcode list was supplied in this session, so none is named anywhere on the site; see Part 5, decision 1.

Coverage page rebuilt. The old page matched a postcode against a hardcoded table of 30 Queensland postcodes and returned an instant yes/no. That table cannot represent a national footprint and would need to become thousands of entries to keep doing what it did. Replaced with a postcode-and-email capture that promises a human confirmation by email before any booking — see Part 6 for the scale reasoning behind this specific choice.

Six testimonials and four "live activity" numbers removed. See Part 4 — this is the one item in this brief with a genuine compliance read, not just a design one.

Fixed a real layout bug affecting every single page. On a phone, the header row (logo + "Book a Collection" button + menu icon) measured 376px wide inside a 355px-wide row on a 390px-wide screen — 16px too wide, on every one of the 31 routes, causing the whole page to drag sideways when touched. The button now reads "Book now" under 480px width; the row no longer overflows at 360, 390 or 430px, confirmed by direct measurement, not visual inspection.

v4.7 — 19 Sep, 17:41 Done c2206a7

Removed the five hand-drawn illustrations in "how a collection actually goes." Each was built from a dozen or more individual SVG shapes (a doormat scene, a scale readout, a delivery van, a washing machine, a folded stack) and had been flagged as reading like amateur clip art rather than considered brand illustration. A smaller version of the same drawings would not answer that critique, so the decision was to remove rather than iterate. The section is now five plain cards: a numeral in a thin outlined circle, a heading, one line of copy, a hairline rule above a short caption — consistent with the numbered-step treatment already used elsewhere on the page. The empty photo slot behind each card (data-photo="jn-N") is untouched, so the photo pipeline built earlier in this session still works unchanged the day real photography exists.

Part 4

AU compliance: what was actioned and why

The one finding in this brief with real exposure

Before this session, the home page displayed to every visitor, as plain fact with no qualifying language: four specific performance numbers (47 loads collected that week, a 26-hour average return time, 12 Kings Club subscribers, a 98% quality pass rate) and six named customer testimonials with suburb and plan attached. All ten were fabricated. The four numbers were literal hardcoded values in the JavaScript (const seed = { col: 47, ret: '26 hrs', sub: 12, sat: '98%' }) with a comment claiming they would be replaced by real database figures "when available" — the code path meant to do that read a database handle (window.db) that does not exist anywhere in the file, so the fabricated numbers would have displayed unconditionally, forever, regardless of the business's real activity level. The testimonials had no submission mechanism, consent record, or real-customer link anywhere in the codebase.

A specific, quantified, factual-sounding claim of business performance, shown to every visitor with no disclaimer, that cannot be evidenced, sits inside the kind of conduct the Australian Consumer Law addresses at s18 (misleading or deceptive conduct) and s29(1)(e)–(f) (false representations about performance characteristics and testimonials specifically). This is not a technical opinion on liability — that question belongs with a solicitor if it is ever asked — it is the factual basis for treating this as the priority item in this session rather than a design preference.

Action taken. The testimonials and their carousel were deleted outright — there was no honest way to keep placeholder social proof. The numbers strip is not deleted: it is hidden (hidden attribute, confirmed removed from the render tree via computed-style check, not just visually collapsed) and will only ever populate from a real database write to config/metrics, using the same live-configuration pattern the site already uses for pricing. Nothing was invented to replace what was removed.

Part 6

Build-for-scale note: the coverage checker

Justification and scale assumption, stated per instruction

Justification. The coverage page previously matched a customer's postcode against a hardcoded JavaScript object of 30 Queensland postcodes and returned an instant yes, "opening soon," or no. That structure is fundamentally a single-city tool: representing genuine national, multi-city coverage the same way would mean a hardcoded list running to thousands of postcode entries, maintained by hand in the site's source code, republished on every change. It does not scale past the city it was written for.

Scale assumption. The instruction given this session was "Australia-wide — the major cities and surrounds, for the time being" — read here as a stated intention to expand beyond a single city within a normal planning horizon, not a permanent one-city business. The coverage mechanism was sized for that: it captures a postcode and an email and promises a human reply, which is exactly as useful at one city as it is at ten, and requires no code change as the footprint grows. The submission lands in the existing coverage collection, already surfaced in the ops dashboard's "Coverage requests" tab — verified in the source, no new ops tooling required.

What this trades away. The old page gave an instant answer; the new one always defers to a human. That is the correct trade while the real footprint is still being defined by Part 5, decision 1 — an instant "yes" today would need to be re-verified against Callum's actual answer regardless.

Part 7

Drafted brief for the solicitor

No legal or tax advice is given in this document. The question below is stated as a fact pattern with options; a solicitor should read it and answer, not this brief.

Fact pattern

LaundryKings' public-facing website, as of this session, states its service area as "Australia's major cities and surrounds" throughout — home page, meta description, structured data read by search engines, and the coverage page. Prior to this session it stated a specific Queensland-only service area (Brisbane, Logan, South East Queensland). The site's Terms of Service (#/terms, clause 12, "Governing law") state: "These terms are governed by the laws of Queensland, Australia, and the courts of Queensland have jurisdiction." This clause was not changed in this session — it was flagged, not touched, because it is a legal drafting question, not a content-accuracy one.

The question

Now that the site markets and, per its own coverage-page copy, intends to actually accept bookings from customers in states other than Queensland, does a Queensland-only governing-law and jurisdiction clause remain appropriate, or does it need a different structure (for example, a clause that still nominates Queensland law but is drafted to properly bind an out-of-state consumer, or a multi-state approach)?

Options as understood by a non-lawyer, for the solicitor to correct or confirm

  1. Recommended starting point (subject to advice): keep Queensland as the nominated governing law and forum, drafted so it is enforceable against a consumer resident in another state — the common approach for an Australian online consumer business operating nationally from a single home state.
  2. A jurisdiction-specific carve-out is needed because operators are engaged locally in each state and local consumer-protection variations apply beyond the national ACL floor.
  3. Some other structure the fact pattern above doesn't anticipate.

Route: Callum Page or Max Jones to forward this section to the firm currently instructed on LaundryKings' Terms and Privacy Policy (both already marked "Draft for legal review — not yet in force" in the source, independent of this session's work).
